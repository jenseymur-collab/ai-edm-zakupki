# ADR-0003: Архитектура — модульный монолит

**Дата:** 2026-05-05
**Статус:** Принято
**Автор:** AI-агент + Ольга

## Контекст

Изначально рассматривались два варианта:
- микросервисы (3 сервиса: Gateway, Core, AI)
- модульный монолит (один сервис с жёстко изолированными модулями)

Ограничения:
- 1,5 дня на разработку
- полный скоуп ТЗ (все 7 функциональных + 4 AI-требования)
- ревьюер — не разработчик
- нужна возможность масштабирования в будущем

## Варианты

### А. Микросервисы (3 сервиса)

**Плюсы:**
- Можно деплоить и масштабировать независимо
- Жёсткие границы между сервисами
- «Профессиональная» архитектура

**Минусы:**
- ~7–9 часов налога на инфраструктуру (Gateway, межсервисные контракты, отдельные деплои, межсервисная отладка)
- Распределённая отладка сложнее для нетехнического ревьюера
- Общая БД между сервисами — анти-паттерн, но без неё за 1,5 дня нельзя
- Реальный смысл микросервисов появляется при >1 команды разработки и >1 паттерна нагрузки

### Б. Модульный монолит

**Плюсы:**
- Все часы идут на функционал
- Один деплой, одна точка отладки
- Жёсткие границы между модулями (на уровне кода и линтинга)
- Каждый модуль готов к выделению в микросервис позже

**Минусы:**
- Не получится показать «у нас микросервисы» (но это не цель MVP)

### В. Гибрид (1 backend + AI как отдельный сервис)

**Плюсы:**
- Только AI вынесен — у него реально другой профиль (медленные внешние вызовы)
- Меньше налога, чем у полноценных микросервисов

**Минусы:**
- Всё равно ~3–4 часа налога
- Половинчатое решение — ни преимуществ монолита, ни преимуществ микросервисов

## Решение

**Вариант Б: модульный монолит.**

Это решение принято на основе арифметики бюджета времени, а не вкуса.

```
Бюджет: 36 часов
Полный скоуп ТЗ: ~22–26 часов
Микросервисы налог: ~7–9 часов
Итог при микросервисах: 29–35 часов = на грани
Итог при монолите: 22–26 часов = с запасом 10+ часов
```

## Архитектурные правила модульного монолита

### Границы модулей (жёсткие)

Каждый модуль — папка в `backend/модули/`. Внутри своя структура:

```
модули/документы/
├── __init__.py        # публичный API модуля (что можно импортировать снаружи)
├── модели.py          # SQLAlchemy-модели (private)
├── схемы.py           # Pydantic DTO (часть public API)
├── сервис.py          # бизнес-логика (private)
├── репозиторий.py     # доступ к БД (private)
└── роуты.py           # HTTP-эндпоинты (private — экспортируются через main)
```

### Что разрешено

- Импортировать **только** через `__init__.py` чужого модуля
- Импортировать общие схемы из `общее/схемы.py`
- Использовать БД через свой `репозиторий.py`

### Что запрещено

- Импортировать из чужого `сервис.py`, `репозиторий.py`, `модели.py` напрямую
- Один модуль читать таблицы другого модуля через ORM
- Циклические зависимости между модулями
- Глобальные переменные с состоянием

### Как обеспечивается соблюдение правил

1. **Линтер.** В `pyproject.toml` пропишем правила `import-linter` или `tach`, которые не дадут нарушить границы.
2. **Code review.** AI-агент при генерации кода явно проверяет границы (см. safety-протокол).
3. **Тесты.** Тесты модуля используют только публичный API модуля.

## Путь к микросервисам в будущем (если понадобится)

Каждый модуль уже изолирован на уровне границ. Чтобы выделить, например, `ai_извлечение` в отдельный сервис, нужно:

1. Создать новый репозиторий, скопировать туда модуль.
2. Заменить прямые вызовы в коде на HTTP-вызовы.
3. Поднять отдельный деплой.

Время на эту операцию: 1–2 дня на модуль. Это не «потом всё переписывать», это «вырезать готовое и обернуть HTTP».

Это оценка ~70% инженерных команд, которые проходили путь монолит → микросервисы (Shopify, Monzo, Stack Overflow и др.).

## Последствия

**Положительные:**
- Успеваем в срок с запасом
- Простая отладка для нетехнического ревьюера
- Чистая архитектура с явными границами
- Готовность к масштабированию

**Отрицательные:**
- Не получится сказать «у нас микросервисы». Но MVP оценивают по продукту, не по слову на ярлыке.
- Один деплой = одна точка отказа. Митигация: на уровне MVP неактуально.
